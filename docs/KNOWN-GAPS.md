# 已知不足（诚实清单）

> 自我审计的结果。补掉的项目移到文末「已补」，未补的保留原因说明。

## 仍然没做（本期）

| # | 项 | 为什么现在不做 |
|---|---|---|
| R1 | 多租户 + PostgreSQL | 只有「团队共用 / 托管」才需要。单机卖家不需要，而提前抽象会拖慢一切。SQL 已按可迁移写（TEXT 主键、ISO 时间、ANSI 风格），真要换是驱动层的事 |
| R2 | iOS 原生 | 与安卓共享同一套 API，但 UI 得重写一遍。收益低于把成交链路做扎实 |
| R3 | RAG 话术库 / A/B 测试 | 需要足够的历史成交邮件才有意义。现在样本为零，做了也是空转。**前置条件已经就位**：改稿留痕（`edit_count`）已经在为这件事积累信号 |
| R4 | 客户门户 | 需要公网部署 + 对外鉴权体系，属于部署形态变化，不是功能缺口 |
| R5 | Docker 镜像未经本机验证 | 本机没装 Docker，只做了 YAML 解析校验。**镜像构建逻辑已写全，但没跑过** —— 首次使用请留意构建日志 |

## 已知的、可以接受的取舍

| 项 | 取舍 |
|---|---|
| 内置离线引擎的产品匹配靠关键词与别名 | 已能跨语言匹配（靠产品库别名），但仍不如真实模型理解同义改写。离线模式定位是「无 Key 也能演示 + 兜底」，不是「替代 LLM」。**别名越全，离线匹配越准** —— 这本身也是给真实模型省的 token |
| 附件 OCR 只输出结构化字段，没有人工校对界面 | 后端链路（落盘 → OCR → 结构化 → 入库）已完整，缺的是 UI |
| WhatsApp 用普通文本消息，未用模板消息 | 模板消息需要 Meta 审核周期，且在 24 小时窗口外才能用。文本在会话窗口内更灵活 |
| 报价单 PDF 依赖 Chrome | 没有 Chrome 时输出 HTML，浏览器「打印为 PDF」效果一致。这是刻意的降级策略，不是缺陷 |

## 已补（v0.2.0）

### 正确性

| # | 原不足 | 现在的行为 |
|---|---|---|
| C1 | 部分行匹配成功时未匹配行被静默丢弃 | 未匹配行写入报价单内部备注、触发 `quote.partial_match` 预警、并**在给客户的回复里明确列出待确认项**；且无论是否开启自动发送，缺行的报价一律停下等人工 |
| C2 | 报价过期后状态停在 `sent`，不登记 `no_response` | 新增 `expire_quotes` 扫描：状态推进为 `expired`，取消待发跟进，超期 7 天后自动登记 `no_response` 并结单。丢单分析终于能看到「客户失联」这一块 |
| C3 | 跟进渠道永远发邮件 | `preferredChannel()` 按客户实际联系方式与会话来源选渠道；WhatsApp 来的客户走 WhatsApp |
| C4 | 45 天内有过往来就判定为「同一询盘回复」 | 收紧为「能看出来才算是回复」：线程匹配 > 回复前缀（Re/AW/回复/返信…）+ 同主题 > 无主题时才用 72 小时近因。老客户谈新项目会正确新建询盘 |
| C5 | 人工改过的草稿不留痕 | 首次改动时保存 `original_subject`/`original_body`，记录改动人；话术排序对「总被改」的模板做**降权**（`edit_count`）。新增改稿率分析接口与一键还原原稿 |

### 产品缺口（成交链路）

| # | 原不足 | 现在的行为 |
|---|---|---|
| P1 | 没有形式发票（PI） | 登记成交 → `quote.accepted` 事件 → 自动生成多语言 PI（含银行信息、付款计划），行项目复用 `quote_items` 避免对账差异。11 种语言，阿语 RTL |
| P2 | 没有回款节点与应收提醒 | 按付款条款自动拆出定金/尾款节点；`sweep_payments` 扫描逾期 → 预警 + 自动起草催款（客户语言，带金额与原始到期日）；支持登记收款、手工加分期 |
| P3 | 没有报价改版与父子关联 | `POST /api/quotes/:id/revise` 生成 v(n+1)，关联父报价、记录改版原因、原报价标记 `superseded`，完整改版链可查 |

### 工程健壮性

| # | 原不足 | 现在的行为 |
|---|---|---|
| E1 | 前端没有 ErrorBoundary | 三层边界（应用外壳 / 页面 / 具体面板）。一个面板渲染出错不再白屏，其余功能照常，可原地重试 |
| E2 | 没有 Dockerfile / compose | 多阶段构建（源码不进镜像）、非 root 运行、含 Chromium 与 Noto 全套字体、健康检查、`shm_size`、日志轮转、卷持久化。**未经本机构建验证** |
| E3 | 冒烟测试没覆盖 WhatsApp / OCR / PI / 回款 / 过期 | 从 51 项扩到 **83 项**，新增 6 个章节，覆盖 PI 与回款、改版链、改稿留痕、回复识别边界、部分匹配守卫、报价过期结单 |
| E4 | 没有请求 ID / 结构化日志 | 每个响应带 `x-request-id`（尊重上游传入），失败与慢请求按结构化字段记录；`/api/health` 回显请求 ID |

### 另外补掉的

| 项 | 说明 |
|---|---|
| 请求体校验 | 原本 11 处 `as never` 强转直接写库，现在所有写接口过 zod 校验，非法输入在边界就以字段级错误拒绝。**全仓库已无 `as never`** |
| 两个数字匹配缺陷 | SKU 里的数字段（`MUG-INSUL-500`）会匹配到任意行里的数量「500」；产品推断用整封邮件做匹配导致每一行都指向同一产品。都会造成错报价，已修并有测试 |
| 离线引擎无法跨语言匹配 | 日文询「ステンレスボトル」曾被打成 USB 扩展坞（靠 SKU 里的「500」撞上「500ml」偶然对上）。现在产品库支持多语言别名，匹配顺序也收紧为「本行 → 主题 → 仅单行时才用整封兜底」，并有跨语言断言守护 |
| 成交下游只走一条路径 | 原本只有 API 的 outcome 接口会触发 PI 与报关；现在 `recordOutcome` 自身发事件，API / 智能体 / 扫描三条路径行为一致 |
| 测试污染生产库 | 冒烟测试曾静默写入真实数据库，已在 v0.1.0 修，此处记录以免回归 |
